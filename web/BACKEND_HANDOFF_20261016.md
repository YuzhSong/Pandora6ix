# Web 管理端后端配合清单（2026-10-16）

本轮用户明确只修改 Web。以下为待协商接口契约及联调验收要求，当前后端未修改，也未部署。日志存储方案尚未由甲方决定。

## 1. 单公司使用与账号归属

- Web 已移除公司开通、部署人员入口和员工自助注册；只维护登录管理员所属公司。
- 当前 `/auth/login` 仍要求 `enterpriseDomain`，Web 保留公司登录标识输入。若需固定甲方标识并取消输入，请后端/部署方提供可信配置，不能在前端凭空写死公司。
- 后端部署需限制企业初始化接口的可用范围。删除前端按钮不等于关闭服务端企业开通能力。
- 员工不得自行注册；`POST /admin/users` 必须仅允许本公司管理员，租户和操作者从会话读取，不接受客户端指定。

## 2. 修改组织类型

现有 `PATCH /admin/org-units/{id}` 已包含 `expectedVersion/name/kind/parentId`，无需另起一套接口。当前 `DirectoryService.patchOrg` 拒绝任何 kind 变更，需后端调整策略后才能真实保存。

Web 已开放部门 ↔ 团队选择，并提交新类型和上级：

```json
{ "expectedVersion": 0, "name": "研发一部", "kind": "DEPARTMENT", "parentId": "company-root-id" }
```

后端需在事务中校验并更新 kind：公司根组织固定；部门归属公司，团队归属部门；禁止自身/后代作为上级；有下级或不匹配的负责人角色时拒绝类型转换。Web 不自动搬迁下级或改动人员角色。版本冲突返回 409；策略拒绝返回可识别错误。需要并发、跨公司引用和权限测试。

## 3. 新增人员同步创建账号及必要资料

沿用一次 `POST /admin/users`，管理员填写登录名和初始密码，由服务端原子创建账号、人员资料和 EMPLOYEE 角色；无需员工另行注册。本轮不擅自规定首次改密、找回密码或账号命名规则。

请后端为创建、编辑和管理员人员列表协商补充以下字段：

| 字段 | Web 提议类型 | 要求 |
| --- | --- | --- |
| `gender` | `MALE` / `FEMALE` / 旧资料 `null` | 新建必填；旧资料兼容 |
| `idNumber` | string / 旧资料 `null` | 新建必填；15 或 18 位基本格式，末位 X 大写；正式证件范围待甲方补充 |
| `phoneNumber` | string / 旧资料 `null` | 新建必填；支持手机号及含区号固定电话，不转为数字 |

其他必填项沿用姓名、登录名、初始密码；组织、职位和直属上级沿用当前契约，不擅自扩充地址、生日等未确认信息。

创建请求包含现有字段 `loginName/password/displayName/orgUnitId/supervisorUserId/jobTitle/roles` 与上表三项。编辑请求沿用 `expectedVersion/displayName/orgUnitId/supervisorUserId/jobTitle/status/roles` 并传递完整个人资料；只改角色时仍保留原个人字段。后端需迁移数据库、进行输入校验，并在事务中持久化；创建失败不得遗留半个账号。

### Web 对旧接口的保护

- `GET /admin/users` 每条记录都返回上述三个键（旧资料可为 null）是本次 Web 提议的兼容约定。后端人员列表仍缺键时，Web 显示待接入提示并在发请求前阻止人员创建及个人字段修改，原有姓名/组织等编辑仍可用。
- 此字段存在性约定需要双方确认，并不证明后端真的持久化；后端不可只添加空字段或回显而不落库。
- 新版创建/编辑返回值必须包含保存后的字段。Web 核验返回值，不一致时不显示成功，并阻止再次提交，提示关闭编辑、刷新核实，避免重复创建。
- 后端接入后必须验收创建 → 员工登录 → 刷新列表 → 编辑 → 重新加载，以及角色变更不清空个人资料、重复登录名、版本冲突和越权访问。
- 身份证只在授权的人员管理接口中返回；人员详情默认脱敏。不得把原始身份证、密码、Bearer token 写入系统日志。现有 `/me`、下属列表及业务用户信息也需审查，避免新增数据库字段后通用映射意外外泄。

## 4. 管理员不接触业务

Web 已删除标签管理页面、编辑入口和 `/tags` 加载/写入，并移除日报、任务、统计导航及页面挂载。已有业务数据和用户此前尚未提交的业务阅读源码未被删除。旧业务 hash 返回人员管理。

后端仍需以权限判断限制业务接口。不能把隐藏导航当作服务端权限控制。公司重要事项保留原有管理范围，本轮未取消。

## 5. 系统操作日志（待甲方敲定）

系统日志用于记录操作事件，与员工工作日报分开。Web 目前只有“尚未启用”的待确认页面，没有真实采集、模拟事件或日志持久化。实际采集必须由后端覆盖 Web、Android 等来源，不能仅靠浏览器记录。

### 拟记录范围

- 已明确：任务新增/修改/删除；工作日报及条目新增/修改/删除。
- 管理追溯：组织、人员账号、角色、公司信息及公司重要事项维护。
- 建议与甲方补充确认：登录失败/退出、审批/撤销/完成/验收等状态变更是否记录。

建议事件包含：事件 ID、服务端时间、公司 ID、可信操作人 ID/显示名、操作类型、对象类型/ID、结果、请求 ID；仅保存必要的脱敏摘要，不复制业务正文。失败操作是否记录、如何关联事务回滚需单独确认。管理员只能读本公司操作事件，不应直接修改或删除事件。

### 甲方待确认事项

| 决策 | 文件 log | 数据库 |
| --- | --- | --- |
| 记录方式 | 结构化日志文件、轮转和归档 | 事件记录、索引和归档 |
| Web 查询 | 需要后端检索/读取服务 | 需要受控分页查询接口 |
| 查询条件 | 确认时间、操作人、对象、操作、结果 | 同左 |
| 运维规则 | 需确认轮转、保留、备份、访问权限 | 需确认容量、保留、备份、访问权限 |

还需确认保留期限、时区、导出权限、是否允许下载、谁能查看、脱敏标准及历史记录是否补录。两种方案均可提供 Web 查询，不能据前端需要单方面定为数据库。甲方确认后另建 OpenSpec 变更实施后端采集、存储及查询接口，再接入 Web 列表与筛选。

## 6. 管理员头像（新增）

用户明确要求只做头像上传界面，等待后端保存接口，不采用本机持久化。仅点击我的账号卡片内头像打开修改弹窗，页头头像进入我的账号，提供 PNG/JPEG/WebP（最大 5 MB）选择和内存预览，保存按钮待接入；正式头像与页头不会被预览替换。

后端需要确认本人头像上传/替换接口、文件大小/类型、服务端图片解码与存储、鉴权、返回的头像地址字段及本人资料读取。需覆盖重新登录/跨设备显示和旧图清理。当前未假定接口 URL，不发送模拟上传请求。

## 7. 公司事项排序（新增）

Web 支持完整列表的拖动与上移/下移/置顶，第一项顺序 1；点击保存后使用现有 `PATCH /company-important-items/{id}` 逐项更新 `displayOrder`，携带原有 title/content/expectedVersion。失败后重新读取服务端实际状态，不声明批量原子成功。

若后续需要批量原子排序，请后端另行提供整组顺序及版本检查接口，避免逐项更新的中间状态。当前 Web 未增加虚构的批量接口。
