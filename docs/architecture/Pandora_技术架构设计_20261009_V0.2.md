| 模块 | 当前工程基线 | 不代表已完成 |

| web/ | React19.2.8声明范围、TypeScript6.0.2、Vite8.3.0基础工程 | 企业/组织/人员/角色/标签管理页面 |

三个独立构建工程确实存在。版本为仓库当前配置，不声称网络上最新版。
保留技术方向，修订业务模型：多日志→日报+条目；员工个人创建/自完成；企业共享标签；任务视图直达详情；消息审核位置已定但仅预留。原A0.1作为历史，不混用其“一日志一项”与“所有完成验收”模型。

## 2. 目标架构

采用模块化单体，先共享后端契约，Android/Web各自独立交付。MySQL8.4/InnoDB为候选，团队评审后才加入依赖及SQL。没有微服务、消息队列、Redis、外部邮件、数据库或AI服务的本轮新增部署。

~~~mermaid
flowchart LR
  A[Android: 导图/视图/日报/我的] --> API[Backend REST与认证边界]
  W[Web: 企业/组织/人员/角色/标签维护] --> API
  API --> IAM[身份及组织授权]
  API --> TASK[任务与审批/完成]
  API --> LOG[日报及工作条目]
  API --> TAG[共享标签]
  API --> READ[导图/日历授权读模型]
  API -. 后续 .-> INBOX[导图消息与审批入口预留]
  IAM --> DB[(候选MySQL)]
  TASK --> DB
  LOG --> DB
  TAG --> DB
  READ --> DB
  INBOX -.-> DB
~~~

Web管理员不是企业创始人，不自动拥有审批权或私人日志读权。前端按钮可见性来自能力集合，但所有操作服务端重校验。

## 3. 模块职责与依赖

| 模块 | 服务职责 | 依赖与禁止事项 |
|---|---|---|
| identity/organization | 认证、会话撤销、所属企业、当前角色、直接上级、管理范围 | 不能从客户端employeeId推断身份；组织变动重新授权 |
| tasks | 创建个人/派发、审核路由、逐人执行、进度、完成来源 | 与审批/验收事务协同；不把进度100%当完成 |
| journals | 同日唯一发布日报、条目修改、历史与草稿边界 | 日报不强制绑定任务；不允许管理者代改 |
| tags | 企业目录、名/色、主次选用、维护权限 | 不扩张对象可见性；非树形分类 |
| dashboard | 四面板授权聚合、十日候选、手动最多十项 | 不用AI摘要；条目ID不冒充日报ID |
| calendar | 区间任务查询，全天/分钟，标签AND | 不读日志；不创建任务副本；渲染不改变业务数据 |
| inbox（Reserved） | 读/已读、消息与reviewId关联、未来审核导航 | 已读≠批准，消息可见≠有审核权 |
| profile/settings | 本人资料、改密、退出、字体/主题 | 组织/角色管理独立；偏好当前采用本机保存 |

建议层次：controller/DTO→application事务用例→domain规则→repository；共享identity范围检查，不把角色if散落在所有页面。具体包名按实施OpenSpec评审，不在本轮重构代码。

## 4. 身份、权限与业务范围

身份上下文来自可信会话。企业ID只从会话/合法管理上下文解析；读取对象先检查企业及管理关系，写操作另校验作者/创建者/接收人/审核人。账号禁用或角色更改要使新权限及时生效，不能永久信任陈旧客户端角色。

能力拆分：createOwnPersonalTask、dispatchToSubordinate、approveDirectSubordinate、createEnterpriseTag、maintainEnterpriseTagsWeb、readOwnJournal、readManagedJournal、editOwnJournal。不使用单个“员工不能创建任务”的开关。

| 动作 | 业务角色/资源条件 |
|---|---|
| 本人个人任务 | 员工、团队长、部门负责人、创始人以本人身份；管理员不因维护权限获得业务身份 |
| 派发他人 | 有派发权的管理人员＋接收人全部在直属/跨级管理范围 |
| 申请审核 | 发起人直接上级；不能只凭同部门或消息链接批准 |
| 个人完成 | 任务为PERSONAL、本人唯一执行关系、已批准 |
| 派发验收 | DELEGATED、创建者、对应完成申请有效 |
| 创建标签 | 部门负责人/创始人；Web管理员维护能力在管理端执行 |
| 选标签 | 对对象有创建/编辑权且标签属于本企业 |
| 管理日志 | 仅范围内阅读；编辑仍限作者 |

highest-no-supervisor没有默认绕过。业务不能确认的节点返回明确待处理状态，不伪造审核人。

## 5. 两类任务工作流

~~~mermaid
flowchart TD
  NEW[创建申请] --> KIND{任务类型}
  KIND -->|PERSONAL| SELF[本人为唯一接收人]
  KIND -->|DELEGATED| PEOPLE[有权下级名单]
  SELF --> REVIEW[发起人直接上级审核]
  PEOPLE --> REVIEW
  REVIEW -->|批准| ACTIVE[执行关系生效]
  REVIEW -->|驳回| REJECT[保留意见及快照/重提规则待确认]
  ACTIVE --> FINISH{类型}
  FINISH -->|PERSONAL| DONESELF[本人标记完成/SELF]
  FINISH -->|DELEGATED| REQUEST[该接收人完成申请]
  REQUEST --> ACCEPT[发起人对该人验收]
  ACCEPT --> DONEACCEPT[完成/CREATOR_ACCEPTANCE]
~~~

task头保存种类、内容、起止、审批；task_assignment保存每个接收人执行/进度/完成来源。PERSONAL只能一个本人，不能以个人类型给其他人派发。DELEGATED按人申请/验收，不能一人的完成覆盖其他人。完成来源与完成时间同事务；不存在“创建者等于接收人所以自动验收”规则。

重要程度保留1–5模型，含义/排序未确认不默认5最高。批准后修改及驳回重提实施等待Q-02；审核记录保存审批版本的内容快照，不能审批后偷偷替换内容。

任务详情删除独立状态UI块，但DTO与数据库状态继续用于权限、操作可用性和追踪。整体完成由负责人判断的旧要求保留，统计和父子汇总未决时不做自动推断。

## 6. 日报、条目与个人事项

work_log为日报头，work_log_entry为多个完整工作内容。唯一键保证同用户同业务日最多一篇发布日报；不是一条工作内容一篇。记录时间与业务日期分别保存。个人事项引用条目ID，可单条全文查看。

~~~mermaid
sequenceDiagram
  participant C as Android
  participant S as Journal服务
  participant D as 数据库
  C->>S: 确认发布(日日期/条目/版本)
  S->>S: 本人、标签、条目内容校验
  S->>D: 事务插入唯一日报和条目
  alt 同日已有日报或并发冲突
    D-->>S: 唯一键冲突
    S-->>C: 409及本人已有日报ID
    C->>S: 读取原篇并补充(新版本)
  else 成功
    D-->>S: 日报/条目稳定ID
    S-->>C: 发布结果
  end
~~~

编辑保持已有条目ID，增补生成新ID。条目移除权限与已选条目失效联动未决，不通过“整篇覆盖删除所有遗漏条目”实现。

个人选择：候选最近十自然日含今日，即业务今日D至D-9，按日期/记录时间近到远。无手动集合且≤10默认全选；>10需人工选择。保存包括空集合，校验作者、已发布、日期及最多十条，事务锁选择状态行/版本，查询不把手动集合重置。保存后导图读模型刷新。到期、移除、编辑正文是否同步/补位按Q-06，不新增自动补位。

日志标签默认关联日报作为当前设计方案；是否条目独立标签待确认。草稿是作者私有，未发布不进管理日志/导图；长期保存和同步方案未决，不增永久草稿系统。

## 7. 标签与视图查询

enterprise_tag共享名/色；task/work_log各有一个primary_tag_id与多标签关系。集合为空→主标签为空；集合非空→主标签必须在集合内，其余为次标签。不同对象可对同一标签设不同角色，不建parent_tag_id。目录权限与任务派发权限独立。

AND：先授权过滤，再要求每项包含全部选中标签。查询可使用分组计数等方案，计数等于去重筛选ID数量；主次均计入。没有筛选标签则不增加标签条件，不按未选标签排除。标签存在不等于任务可见。任务颜色读取主标签颜色；日志显示名但不染色。

calendar返回同一任务和时间范围。显示端以视图范围裁剪，月历跨周分段只是绘制片段；同任务各片段同ID。日/周按全天或分钟，拥挤布局仅渲染策略。历史日期不设十天业务限制，查询窗口/分页是性能控制。六周月份按实际覆盖，不能固定35天造成遗漏。

## 8. 消息审核预留

未来导图消息面板处理任务审批，日志页不放信封。inbox_message关联recipient、task、review；同事务或可靠重试生成待审批/结果消息的方案留给后续实现。不添加MQ/SMTP依赖。读/已读本人的消息仍需授权；动作单独检查review.reviewer，不因已读自动批准或因消息存在获得审批权。

本轮只产出接口与字段契约；批准流程是核心业务，不因为审批UI未实现改成免审。最高级审核、审批后修改等未决应阻塞相关正式操作，而不是客户端偷偷默认通过。

## 9. 账号与显示设置

- 资料读取当前身份，Web组织维护独立。
- 改密验证当前身份与当前密码，服务端安全哈希保存，密码不进日志/响应；成功撤销相关旧会话为安全设计提案，具体会话实现经评审。
- 退出撤销当前会话、客户端清凭据/私有缓存；已发布业务内容不删除。
- 字体/显示、主题偏好本机按用户隔离保存，退出不把他人偏好/私有缓存混用。无跨设备同步需求，不建user_preferences表。
- 认证采用可撤销会话/令牌抽象；JWT、刷新令牌、Session等最终选择待安全实现方案，不承诺已部署。

## 10. 事务与错误设计

| 用例 | 原子范围/并发 |
|---|---|
| 日报发布 | 头+所有条目+标签；唯一键，重复请求映射原结果 |
| 日报补充 | 校验version；条目增改+标签，同事务，不丢条目 |
| 个人选择 | 状态版本+选择行替换，≤10服务校验，空集合有手动状态 |
| 任务申请 | task+assignment候选+review快照+标签，全部合法才写入 |
| 批准申请 | 审核决定+审批状态+相关执行关系生效 |
| 完成个人 | 校验本人、批准、种类；完成来源/时间/版本 |
| 派发验收 | 对应完成申请+执行完成事实/时间/来源 |
| 标签更新 | 本企业角色、标签版本；不扩大关联对象权限 |

统一API错误；重试幂等与乐观冲突明确，不能“保存成功但其中多人没派发”。消息后续采用一致性策略时不使已读与批准耦合。

## 12. 实施顺序与验证边界

评审本套文档→确认相关Q→新实施OpenSpec→身份组织与共享标签→任务个人/派发两分支→日报条目及选择→视图/设置→后续导图消息审批。模块继续独立构建，正式业务代码、依赖、SQL和测试不属于本轮。

本版有流程/时序Mermaid源码，尚未渲染图形验收。没有实际数据库事务、业务API响应、三端联调或性能测试结果。
