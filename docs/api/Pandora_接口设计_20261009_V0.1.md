# Pandora 接口设计 API0.1

2026-10-09；LoFi；首版正式业务契约草案，不是已实现接口清单。
当前backend仅健康检查；本文件所有/api/v1业务路由均未实现或运行验证。
依据[需求V1.3](../requirements/Pandora_第二章_20261009确认修订版_V1.3.md)，配套[A0.2](../architecture/Pandora_技术架构设计_20261009_V0.2.md)、[DB0.2](../database/Pandora_数据库设计_20261009_V0.2.md)。
下面“Planned”为后续核心实施设计；“Reserved”为本次只预留、不能排进已完成业务。路由命名等技术提案需团队评审，后续可转OpenAPI并做契约测试。

## 1. 公共契约

- 前缀/api/v1；JSON；业务ID字符串（避免JS整数精度问题）。
- 认证来自可撤销会话，具体Session/JWT实现待安全设计。不要通过body.role、authorId、creatorId或enterpriseId伪造身份。
- 服务端按当前企业、角色、直属/跨级管理范围、对象归属与状态重校验；跨企业对象按统一不可访问策略，不泄露私有ID。
- 日期YYYY-MM-DD，日内时刻HH:mm（分钟，拒绝带秒或静默取整）；记录事件UTC ISO8601；业务时区Q-04确定后统一。接口可回传当前已配置businessTimezone，未配置需明确错误，不按客户端时区偷偷改业务日。
- 可变资源返回version；变更命令expectedVersion必填，冲突409；普通发布/提交可用Idempotency-Key，技术幂等存储及期限待实现，不额外创造消息队列。
- 标准成功为{"data":...,"requestId":"..."}；分页data={"items":[],"nextCursor":null}；失败{"error":{"code":"...","message":"...","fieldErrors":[]},"requestId":"..."}。
- 读取列表limit建议20、允许1–100（技术分页，不是业务数据上限），opaque cursor；排序包含id保证稳定。区间查询限制单次窗口并允许分页/分次加载，不限制能查看很早的业务日期。
- 标签参数tagIds重复去重；空集合不筛选，多个为AND；只匹配已授权任务。不新增OR切换或标签层级语法。
- 个人任务和派发任务都有审批生效；审批UI预留不能让后端跳过批准。

## 2. 统一错误

| HTTP | code示例 | 预期 |
|---|---|---|
| 401 | UNAUTHENTICATED/SESSION_REVOKED | 重新认证；不清除已发布业务数据 |
| 403 | FORBIDDEN/RECIPIENT_OUT_OF_SCOPE | 拒绝越权；不靠客户端隐藏 |
| 404 | RESOURCE_NOT_FOUND | 不存在或按策略不可见 |
| 409 | VERSION_CONFLICT | 重新读取后处理，不自动覆盖 |
| 409 | DAILY_JOURNAL_EXISTS | 返回本人同日日报ID；引导编辑原篇 |
| 409 | INVALID_WORKFLOW_STATE | 未批、已完成或已决定不能执行该动作 |
| 409 | WORKFLOW_POLICY_UNCONFIRMED | 无上级等尚未定义，明确不能自动免审 |
| 422 | VALIDATION_FAILED/TAG_SET_INVALID | 字段、时间、主标签集合错误 |
| 422 | TOO_MANY_IMPORTANT_ENTRIES/ENTRY_NOT_ELIGIBLE | 超十/不是本人已发布十日条目 |
| 422 | PERSONAL_RECIPIENT_INVALID | 个人任务企图派他人 |
| 500/503 | INTERNAL_ERROR/SERVICE_UNAVAILABLE | 回滚原子业务，requestId用于定位；不暴露SQL/密码 |

角色拒绝用403；数据无权与不存在统一暴露策略在安全实施时固定，不能对不同私有资源返回可枚举详情。错误message不给敏感他人资料。

## 4. 企业标签

| 方法/路由 | 行为 | 权限/约束 | 状态 |
|---|---|---|---|
| GET /tags | 企业目录，分页、name查询 | 已登录本企业，选用不改变对象读权 | Planned |
| POST /tags | {name,colorHex}→Tag | 部门负责人/创始人创建；Web管理员维护目录路径亦可调用 | Planned |
| PATCH /tags/{id} | {name?,colorHex?,expectedVersion} | Web本企业管理员维护；不自动授予创建者维护他人标签 | Planned |

Tag={id,name,colorHex,version}。colorHex候选#RRGGBB，名称非空；长度/颜色格式为技术校验。是否同名禁止未确认，不以冲突409强加唯一名称。
Task/Journal中tagIds可[]、primaryTagId可null；非空时primary在tagIds内且仅一个；其余次标签，不重复。同企业标签才能关联。“第一标签颜色”以明确primaryTagId契约实现，不依赖JSON对象迭代顺序。任务响应可提供由主标签解析的displayColor；日报不提供染色指令。

## 5. 任务与接收人

### 5.1 查询、@候选与创建

| 方法/路由 | 行为/参数 | 权限 | 状态 |
|---|---|---|---|
| GET /tasks | from/to、scope=mine/managed/created、tagIds、cursor/limit | scope也需服务端校验，managed仅有权范围 | Planned |
| GET /tasks/{taskId} | 任务全文、时间、标签、本人/有权执行关系、allowedActions | 已授权对象 | Planned |
| GET /tasks/recipient-candidates | q、cursor/limit，@后检索姓名/组织 | 有派发权管理者，结果含直属/跨级下级 | Planned |
| POST /tasks | TaskCreate→申请结果 | 个人或派发分支分别校验 | Planned |
| PATCH /tasks/{id} | 内容编辑、expectedVersion | 创建者、允许阶段；获批编辑范围Q-02 | Conditional，未决阶段不开放 |
| POST /tasks/{id}/resubmit | 暂不定请求 | 重建vs原任务重提Q-02 | Pending |

TaskCreate契约：

~~~json
{
  "kind": "PERSONAL",
  "title": "准备客户交流材料",
  "description": "补充说明，可为空",
  "priorityLevel": 3,
  "timeKind": "TIMED",
  "startDate": "2026-10-09",
  "endDate": "2026-10-09",
  "startTime": "09:15",
  "endTime": "10:40",
  "recipientIds": ["CURRENT_USER_ID"],
  "tagIds": ["TAG_A", "TAG_B"],
  "primaryTagId": "TAG_A"
}
~~~

- PERSONAL：只有本人，服务端把本人作为唯一执行人；请求包含其他接收人→拒绝，不默默替换。普通员工可创建此类，不获得派他人或拆分权限。
- DELEGATED：一人或多人，所有接收人属于当前管理范围；非法一个则整笔拒绝，不部分派发。
- ALL_DAY：startTime/endTime均null；TIMED两项均HH:mm。日期范围合法；跨日/同刻端点Q-04未决。重要程度1–5，值高低排序Q-05未定。
- 无标签→tagIds=[]/primary=null；主标签必须在集合中。
- 创建成功201只表示申请已提交：taskId/reviewId/reviewStatus=PENDING、assignments=PENDING_APPROVAL；不是正式派发。找不到直接上级按Q-01返回明确未决，不创建自审记录。
- parentTaskId未加入最终TaskCreate必填/可选契约，因为US39/Q-07仍未确认；以后新增不会强制所有任务有关联。

TaskDetail包含kind、title、description、时间字段、priorityLevel、tags/primary、reviewStatus、version、authorizedAssignments及allowedActions。状态保留后台/响应，客户端删除独立“当前状态”块即可。多人分配信息是否可看全部仍按角色对象范围，不向普通接收人默认泄露全企业。

### 5.2 进度与两类完成

| 方法/路由 | 请求/结果 | 权限/流程 |
|---|---|---|
| POST /task-assignments/{id}/progress-records | {progressPercent,note,expectedVersion}→记录/当前版本 | 该接收人，已批准有效关系；0–100，100不自动完成 |
| POST /tasks/{id}/complete | {expectedAssignmentVersion}→本人assignment完成事实 | PERSONAL、本人、已批准；completionSource=SELF |
| POST /task-assignments/{id}/completion-requests | {note?,expectedVersion}→待验收 | DELEGATED、该接收人、有效关系 |
| POST /task-completion-requests/{id}/decision | {decision:ACCEPT/REJECT,comment?,expectedVersion} | DELEGATED创建者逐人验收；accept来源CREATOR_ACCEPTANCE |

均Planned，未实现。个人complete的版本是本人执行关系version（明确命名expectedAssignmentVersion），不是task内容version；其他命令expectedVersion对应路由目标资源。个人complete拒绝DELEGATED；完成申请拒绝PERSONAL。重复同一幂等请求返回原结果，不追加第二完成时间；不同操作对已完成关系返回状态冲突。验收更新请求决定、该人完成源与时间同事务，其余接收人不变。状态“审核驳回”和“验收拒绝”不同。
任务删除、取消、转交等没有本轮确认依据，不添加操作。

## 6. 日/周/月读模型

GET /calendar?mode=day|week|month&anchorDate=YYYY-MM-DD&tagIds=... 为Planned。
返回{mode,anchorDate,rangeStart,rangeEnd,today,businessTimezone,tasks:[同TaskSummary],nextCursor?}：
- range采用选模式完整范围；周一到周日，月首尾完整周，包括四/五/六周月份；时区确定后计算。
- 授权任务与选区间重叠，时间均源自task；无logs/workEntries字段。
- 标签AND；全天/定时任务分别标记，显示端按具体时间排布；同任务横条分片ID不变。
- 分页/容量不足必须能查看全部任务；数量提示按授权且过滤后数据计算，不是数据库查询limit导致少算。
- 任务点击→GET /tasks/{id}，不触发GET calendar的新模式；模式改变仅用户手动。日期定位和回今天只改anchorDate。
- 单次窗口限制只是技术保护，可查询任何有权限且存在数据的历史日期；不复用十日候选限制。

日历DTO不存title缩略后的正文，也不把像素宽度/行高写数据库。跨日时刻端点未确认时，不声称已确定特定日历覆盖时刻。

## 7. 日报与工作条目

| 方法/路由 | 行为 | 权限/限制 | 状态 |
|---|---|---|---|
| GET /work-logs | date/from/to、scope=mine/managed、cursor/limit | 作者本人或管理范围内，只读他人 | Planned |
| GET /work-logs/{id} | 日报头、工作条目、tags/primary、version | 同上 | Planned |
| POST /work-logs | JournalCreate→唯一日报与稳定条目IDs | 作者本人；同业务日最多一篇 | Planned |
| PATCH /work-logs/{id} | 更新/增补条目与标签、expectedVersion | 作者本人，冲突不覆盖 | Planned |
| GET /work-log-entries/{id} | 单条content/recordedAt/journalId/workDate/作者 | 作者或有权管理者；不返回同篇全部条目 | Planned |
| 草稿同步/条目删除API | 未定义 | 长期草稿Q-03、移除Q-06 | Pending |

JournalCreate={workDate,entries:[{clientEntryKey,content}],tagIds:[],primaryTagId:null}。作者从会话获得。正文非空与至少一条作为有效发布的设计校验；空草稿不可发布。clientEntryKey用于重试/映射临时条目，不成为业务ID。
201→journalId/version、各条entryId映射。已有篇409 DAILY_JOURNAL_EXISTS返回本人existingJournalId，不把失败请求内容自动塞入原篇；用户读取后补充。

JournalPatch={expectedVersion,upsertEntries:[{entryId?,clientEntryKey?,content}],tagIds?,primaryTagId?}：
已有entryId必须属于本人该篇，修改保留ID；无entryId为增补；遗漏旧条目不删除。标签集合省略表示不改，提供空集表示清标签且primary需null。条目增加/正文/标签与头version同事务，成功返回新版本。
发布确认、放弃未保存确认是客户端交互，但后端不将未确认的草稿公开；本轮草稿长期持久化未定，不编造draft POST及同步表。
日志不强制关联任务，不含required taskId。可选关联Q-08未定；不添加关联接口。日志标签默认整篇粒度，不含entryTagIds，日志不返回染色字段。
今日/历史分区、首屏5再展开5为客户端分页呈现，不限制后台只保存十篇。

## 9. 导图消息及任务审批（全部Reserved）

| 方法/路由 | 契约 | 权限 |
|---|---|---|
| GET /inbox | 当前本人消息分页/未读，messageId/type/taskId?/reviewId? | 消息recipient本人 |
| PATCH /inbox/{id}/read | {read:true}→已读时间 | 本人；不写审批决定 |
| GET /task-reviews | pending/created及分页 | reviewer或提交者合法范围 |
| GET /task-reviews/{id} | 审批内容快照、决定、批注、版本、allowedActions | reviewer/提交者授权 |
| POST /task-reviews/{id}/decision | {decision:APPROVE/REJECT,comment?,expectedVersion} | 指定直接上级，pending内容版本有效 |

Reserved意味着只设计不实施服务/页面，不代表审批业务取消。未来导图消息带reviewId打开审核，拿到消息ID后仍要重新查review权限；已读不批准。
APPROVE原子写审批决定、task.reviewStatus和候选assignment生效；REJECT不派发，保存意见。任务创建者可见自身申请结果，不可代审核。无上级处理、原任务重提、批准后改内容Q-01/02不在此自动敲定。
消息types/历史/批注必填程度与事件重试属于后续实现评审，不额外添加SMTP、外部邮件或AI助手。

## 10. 数据状态与兼容性

| 数据概念 | 候选枚举 | 不能混用 |
|---|---|---|
| task.kind | PERSONAL/DELEGATED | 创建范围及完成流程 |
| task.reviewStatus | PENDING/APPROVED/REJECTED | 不是任务完成状态 |
| assignment.executionStatus | PENDING_APPROVAL/ACTIVE/AWAITING_ACCEPTANCE/COMPLETED | 逐人状态，不等于全任务完成 |
| completionSource | SELF/CREATOR_ACCEPTANCE/null | 与kind匹配，未完成null |
| timeKind | ALL_DAY/TIMED | 与kind独立 |
| 标签角色 | primaryTagId+tagIds | 非父子分类目录 |

上述技术码评审后固定，客户端未知枚举给兼容提示、不自行显示成功。删除状态视觉块不使服务端不返回状态。图表颜色不是API权限标识。ID/date/minute/version契约三端统一，原LoFi模拟结构不能直接冒充正式API DTO。

## 11. 实施前与契约验收

- 先确认Q-01至09中影响当前接口的项；不得为未知审批路径写自动approve=true。
- 确定身份域、时区、长度、会话方案、错误暴露策略、幂等机制后转OpenAPI。
- 核心测试：唯一日报冲突、稳定条目ID、多选≤10和空集合、标签AND/跨企业、个人自完vs逐人验收、撤销会话、分页全部数据。
- Reserved测试此时是设计审查，服务返回和运行截图均未生成。
- 本版不声称路由已经存在、Swagger已生成、数据库已建、接口联调成功或三端功能全部完成。
