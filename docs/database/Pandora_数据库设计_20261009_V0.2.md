# Pandora 数据库设计 DB0.2

2026-10-09；最初设计于LoFi，本次在backend-syz整理送审；逻辑设计草案，没有执行DDL、建库、迁移或业务数据验证。
依据[需求V1.3](../requirements/Pandora_产品需求与设计文档_20261009确认修订版_V1.3.md)，配套[A0.2](../architecture/Pandora_技术架构设计_20261009_V0.2.md)、[API0.1](../api/Pandora_接口设计_20261009_V0.1.md)。

## 1. 边界与计数

MySQL8.4/InnoDB为候选，不代表仓库已有MySQL依赖。18个核心候选实体：
enterprise、org_unit、app_user、role、user_role、task、task_review、task_assignment、task_progress_record、task_completion_request、work_log、work_log_entry、company_important_item、personal_important_selection_state、personal_important_selection、enterprise_tag、task_tag、work_log_tag。
另有1个预留inbox_message，合计19个逻辑实体；不自动实施。

相对DB0.1：增加工作条目及3个标签实体，重要事项引用条目；日报每日唯一；新增task_kind和完成来源；消息审核有预留映射。本机显示偏好不新增数据库表。草稿、父子关联、停用历史等仍待规则确定。

## 2. 公共字段与键规范

- 主业务ID候选BIGINT UNSIGNED，API以字符串传输；role.code例外为VARCHAR。ID方案最终实施评审。
- 所有企业业务表含enterprise_id BIGINT NOT NULL。实体表id主键，另建显式UNIQUE(enterprise_id,id)供复合外键引用；不可依赖MySQL非唯一引用键。
- created_at/updated_at采用DATETIME(6) NOT NULL存UTC；业务日期是DATE，业务时区按Q-04确认后配置，不用UTC日期误判日报唯一。
- 可变聚合含version BIGINT NOT NULL默认0；更新WHERE version=expected并原子递增。
- 字符编码utf8mb4。VARCHAR长度是存储建议，不自行升级为甲方业务字数限制；接口边界必须一致后才实施。
- 同企业引用用(enterprise_id,object_id)复合FK；可选外键允许NULL，其余NOT NULL。删改默认RESTRICT，不连锁删除日志/审批历史。
- 带“作者保护”的键显式增加UNIQUE(enterprise_id,author_user_id,id)，支撑条目/个人选择复合引用，避免跨用户绑定。
- 表中N为NOT NULL，Y为可空；共享created_at等未重复列出的字段遵循上述规范。
- 跨表数量、角色、管理范围、标签主集合一致性不能靠CHECK实现，必须服务端事务校验。

## 4. 身份/组织实体

| 表 | 专用字段（类型；空值） | 约束/说明 |
|---|---|---|
| enterprise | name VARCHAR(128) N；status VARCHAR(24) N；business_timezone VARCHAR(64) Y | 时区字段预留配置，取值待Q-04；不擅自固定“所有企业上海” |
| org_unit | name VARCHAR(128) N；kind VARCHAR(24) N；parent_id BIGINT Y | 同企业自FK；公司/部门/团队；防环服务校验 |
| app_user | login_name VARCHAR(128) N；password_hash VARCHAR(255) N；display_name VARCHAR(128) N；org_unit_id BIGINT Y；supervisor_user_id BIGINT Y；job_title VARCHAR(128) Y；status VARCHAR(24) N；version BIGINT N | UNIQUE(enterprise_id,login_name)；组织/直接上级同企业FK；密码非明文 |
| role | code VARCHAR(32) PK；name VARCHAR(64) N | ADMIN/FOUNDER/DEPARTMENT_MANAGER/TEAM_LEAD/EMPLOYEE候选固定码，不数字高低比较 |
| user_role | enterprise_id N；user_id BIGINT N；role_code VARCHAR(32) N | PK(enterprise_id,user_id,role_code)，用户复合FK及role FK |

直接上级空不自动表示免审。管理员不获得普通业务管理权。登录域、改密及会话撤销机制实施前设计；本文件不为未选定Session/JWT强加会话表。密码改后会话撤销为安全方案。

## 5. 任务实体

### 5.1 task（任务申请与内容头）

| 字段 | 类型/空值 | 说明 |
|---|---|---|
| creator_user_id | BIGINT N | 同企业创建者 |
| task_kind | VARCHAR(24) N | PERSONAL或DELEGATED；创建后种类不得通过普通编辑偷换 |
| title | VARCHAR(255) N | 任务名称 |
| description | TEXT Y | 任务备注/说明 |
| priority_level | TINYINT N | 1–5；高低排序Q-05 |
| start_date/end_date | DATE N | 日期范围，end>=start |
| time_kind | VARCHAR(24) N | ALL_DAY或TIMED |
| start_minute/end_minute | SMALLINT Y | 0–1439的日内分钟；API HH:mm；全天均NULL，定时均非NULL |
| review_status | VARCHAR(24) N | PENDING/APPROVED/REJECTED候选，不等于执行状态 |
| primary_tag_id | BIGINT Y | 同企业enterprise_tag FK；空标签集合时NULL |
| version | BIGINT N | 审批快照/并发内容版本 |

记录task_kind与time_kind不合并；“个人”不是“全天”。时间字段不含秒避免丢精度。TIMED同刻/跨日端点和UTC转换在Q-04确认后实施，日期有效性可先确认；不偷偷用默认小时填全天。无overall_complete推导字段，因为多人/父子整体规则仍未决。

### 5.2 task_review（审批尝试与不可变内容快照）

| 字段 | 类型/空值 | 说明 |
|---|---|---|
| task_id | BIGINT N | 同企业任务FK |
| attempt_no | INT N | UNIQUE(enterprise_id,task_id,attempt_no) |
| submitted_by_user_id | BIGINT N | 申请创建者，服务验证 |
| reviewer_user_id | BIGINT N | 提交时直接上级，不按查看者自动生成 |
| task_version | BIGINT N | 本次审批内容版本 |
| submitted_snapshot | JSON N | kind、名称、说明、时间、接收人IDs、标签IDs/主标签、重要程度 |
| decision | VARCHAR(24) N | PENDING/APPROVED/REJECTED |
| comment | TEXT Y | 审核意见/批注契约预留 |
| submitted_at | DATETIME(6) N | UTC |
| decided_at | DATETIME(6) Y | 未决定NULL，决定后非NULL |
| version | BIGINT N | 决定竞争控制 |

已决定记录不可被下一轮覆盖。重提路由未开放前，不把attempt模型当已确认“驳回原任务重提”。无上级不生成假reviewer或自审记录。

### 5.3 task_assignment（每接收人执行事实）

| 字段 | 类型/空值 | 说明 |
|---|---|---|
| task_id/recipient_user_id | BIGINT N | 同企业任务/接收人FK；UNIQUE(enterprise_id,task_id,recipient_user_id) |
| execution_status | VARCHAR(32) N | PENDING_APPROVAL/ACTIVE/AWAITING_ACCEPTANCE/COMPLETED候选 |
| progress_percent | TINYINT N | 0–100；不自动认定完成 |
| activated_at | DATETIME(6) Y | 批准生效后记录 |
| completion_source | VARCHAR(32) Y | SELF或CREATOR_ACCEPTANCE；未完成NULL |
| completed_by_user_id | BIGINT Y | PERSONAL本人或DELEGATED验收创建者 |
| completed_at | DATETIME(6) Y | 真实完成事实；非截止日期 |
| version | BIGINT N | 并发 |

PERSONAL结构必须仅一个creator的关系；跨表种类/人数/身份用创建事务检查。完成源与task_kind相容，用事务而非伪造跨表CHECK。COMPLETE要求三完成字段同时非NULL，未完成同时NULL；进度100%可以尚未完成，完成是否统一进度值留给操作设计，不用进度反推事实。

### 5.4 task_progress_record

assignment_id BIGINT N（同企业FK）、actor_user_id BIGINT N、progress_percent TINYINT N、note TEXT Y、recorded_at DATETIME(6) N。追加历史，不只覆盖当前值；范围0–100；操作者必须该接收人。assignment当前值与记录同事务。

### 5.5 task_completion_request

assignment_id BIGINT N、requested_by_user_id BIGINT N、submitted_note TEXT Y、requested_at DATETIME(6) N、decision VARCHAR(24) N（PENDING/ACCEPTED/REJECTED）、decided_by_user_id BIGINT Y、decision_note TEXT Y、decided_at DATETIME(6) Y、version BIGINT N。
仅DELEGATED使用；接收人申请，发起人验收；PERSONAL不创建此记录。一次只能有一条待验收申请，由assignment行锁/事务保证，不使用缺乏条件索引的“全部唯一”。记录验收决定和assignment完成事实同事务；拒绝验收不等于拒绝派发审批。

## 6. 日报与工作条目

### 6.1 work_log（已发布日报头）

| 字段 | 类型/空值 | 说明 |
|---|---|---|
| author_user_id | BIGINT N | 同企业作者FK |
| work_date | DATE N | 业务自然日，UNIQUE(enterprise_id,author_user_id,work_date) |
| primary_tag_id | BIGINT Y | 同企业标签；日志仍不染色 |
| published_at | DATETIME(6) N | 初次发布UTC时间 |
| version | BIGINT N | 头/条目/标签聚合共同版本 |

不在这里存唯一“一句话content”代替全部条目。至少一条非空工作内容由发布事务校验（有效日报的设计约束，空草稿不发布）。发布表不混入草稿，以免草稿误进管理读取或触发日报唯一性。长期草稿存储另设计，不创建多个“发布日报”绕过规则。

### 6.2 work_log_entry（完整工作内容）

| 字段 | 类型/空值 | 说明 |
|---|---|---|
| author_user_id | BIGINT N | 保留作者保护复合键，必须同日报作者 |
| work_log_id | BIGINT N | FK(enterprise_id,author_user_id,work_log_id)→日报(enterprise_id,author_user_id,id) |
| content | TEXT N | 完整工作内容，不AI摘要，不拆短标题作为原文 |
| recorded_at | DATETIME(6) N | 该条记录时间UTC，编辑不伪装新建 |
| display_order | INT N | 篇内顺序技术字段 |
| version | BIGINT N | 条目变更跟踪 |

显式UNIQUE(enterprise_id,author_user_id,id)。修改保持ID，新增生成新ID。日日期从日报读取，不重复保存易冲突的work_date；查询按父日期近到远、recorded_at、id稳定排序。条目移除/失效与选中联动Q-06，当前API不默默删除遗漏条目。
日报标签为当前设计粒度；无entry_tag表，不冒充甲方已确认条目独立标签。

## 7. 公司事项与个人选择

| 表 | 字段 | 约束/说明 |
|---|---|---|
| company_important_item | publisher_user_id BIGINT N；title VARCHAR(255) N；content TEXT Y；display_order INT N；version BIGINT N | 发布/维护权限按旧需求；展示单行不截断存储 |
| personal_important_selection_state | owner_user_id BIGINT N；has_manual_selection BOOLEAN N；version BIGINT N | PK(enterprise_id,owner_user_id)，锁行；无记录表示未手动保存，不建独立无意义id |
| personal_important_selection | owner_user_id BIGINT N；entry_id BIGINT N；display_order INT N | PK(enterprise_id,owner_user_id,entry_id)；FK状态；FK(enterprise_id,owner_user_id,entry_id)→条目作者键 |

注意state/selection无id主键，公共实体id规范在此用实际复合PK代替。
保存替换选择集合与state.version同事务；≤10、已发布、最近十日候选服务校验；保存空集合仍has_manual_selection=true。默认不持久化为用户手动选择，候选>10不自行选前十。
已选条目过期或移除不通过FK级联偷偷决定业务；正文同步、失效提示/剔除和补位仍Q-06。授权窗口不能因客户端缓存过去ID而绕过。

## 8. 企业标签与对象关联

### 8.1 enterprise_tag

name VARCHAR(64) N、color_hex CHAR(7) N（候选#RRGGBB）、created_by_user_id BIGINT N、version BIGINT N。
标签属于企业，部门负责人/创始人可创建，Web管理员维护，团队长/员工只选用。名称非空/颜色格式服务验证；名称重复是否禁止未确认，不自行建立唯一名称业务规则。颜色只属于目录，不把color复制进task成为第二来源。
停用/删除及历史颜色策略Q-09；不因维护要求默认允许物理删除已关联标签。可追加enabled等字段须在策略确认后设计。

### 8.2 task_tag

PK(enterprise_id,task_id,tag_id)；task_id/tag_id BIGINT N分别同企业FK；secondary_order INT N用于次标签显示顺序。没有“一级标签目录/二级标签父节点”。主标签身份以task.primary_tag_id为准，排序不是颜色依据。

### 8.3 work_log_tag

PK(enterprise_id,work_log_id,tag_id)；两字段BIGINT N分别同企业FK；secondary_order INT N。和task_tag相同catalog，primary_tag_id在日报。日志不染色但保留选用标签信息。

### 8.4 主标签及关系一致性

对象为空集合→primary=NULL；非空集合→exactly one primary且在集合中。单列primary保证最多一个，但“在集合中”和“非空必有主”需聚合事务校验。只给primary到tag的FK不代表已保证其在关系表。
更新关系后校验/设置primary再提交，不因关系表与对象循环引用添加不可实现约束。
AND筛选以去重tagIds数作为必须命中数，授权任务先过滤，主次都来自同关系集合。

## 9. inbox_message（Reserved，不实施）

recipient_user_id BIGINT N、type VARCHAR(32) N、task_id BIGINT Y、review_id BIGINT Y、title VARCHAR(255) N、created_at DATETIME(6) N、read_at DATETIME(6) Y。
同企业用户/task/review复合FK。审核消息要求review_id非空并验证review所属task和接收人；其他提醒可无review_id，不强制所有消息审批。候选类型REVIEW_PENDING/REVIEW_RESULT/TASK_NOTICE，具体扩展不自动实现。
服务按事件/接收人幂等避免重复；若以review+type+recipient唯一，需考虑NULL消息分支不能依赖NULL唯一性。字段可在实现时补event_key作为技术幂等键，当前不假称字段已入库。
读自己的消息不授权审核；直接上级权限另验。已读仅read_at，不能更新审批decision。删除日志信封不删除这个预留模型，不接真实邮件SMTP。

## 10. 外键与删除政策

同企业实体父键显式唯一，再由子(enterprise_id,fk_id)引用。日报/条目保护作者的三列目标显式唯一；selection只能关联同一owner条目。单enterprise_id必须引用enterprise，禁止跨企业role/user关系。
目录和组织删除默认限制，有历史引用不物理级联；账号禁用不删除日志/任务。是否匿名化/归档/停用按后续合规及业务策略确认，不能本轮添加正式删除功能。
可选主标签NULL允许，但必填业务字段必须NOT NULL；MySQL CHECK在UNKNOWN时可能通过，因此分钟规则必须明确ALL_DAY两NULL或TIMED两非NULL且0–1439，不只写范围CHECK。

| 查询 | 索引/键 |

| 作者日期日报及唯一性 | UNIQUE work_log(enterprise_id,author_user_id,work_date) |
| 日报条目/稳定排序 | work_log_entry(enterprise_id,work_log_id,recorded_at,id) |
| 接收人的任务 | task_assignment(enterprise_id,recipient_user_id,execution_status,task_id) |

## 12. 事务与安全验证计划

1. 同日并发发布：唯一键只一日报；失败返回本人已有ID，不能泄露别人。
2. 编辑/选择expectedVersion不匹配→409，无静默覆盖；选择新条目校验十日、作者、已发布与≤10。
3. 创建任务：kind/接收人/直接上级/标签/时间全验证；快照、候选关系同事务；未批准不能激活。
4. 个人完成：本人、唯一本人关系、批准、kind；完成源SELF/时间同事务，重试不能产生第二完成。
5. 派发验收：创建者、合法pending请求；对应assignment来源CREATOR_ACCEPTANCE/时间同事务，其他人不变。
6. 标签：同企业FK防跨租户；关系与主标签在同事务；筛选不得返回未授权对象。
7. 消息：只有本人读/已读，审核必须另查reviewer；消息已读不批准。
8. 密码/会话/偏好：不记录明文，不将本机设置当后端权限，没有“退出删除日报”。

上述是待实施测试，不是DB测试结果。Q-01–09见需求2.12，正式DDL不得先偷偷填补其业务值。

## 13. 官方技术约束参考

[MySQL8.4外键](https://dev.mysql.com/doc/refman/8.4/en/create-table-foreign-keys.html)用于复合/唯一引用键；[CHECK约束](https://dev.mysql.com/doc/refman/8.4/en/create-table-check-constraints.html)用于NULL语义与行内约束。跨行计数及角色权限须在应用事务校验，不能将候选方案写成SQL已验证。
