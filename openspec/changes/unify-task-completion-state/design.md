## Context

当前 task_assignment 分别保存执行状态；完成申请指向提交人的 assignment，验收仅改变一个 assignment。Android 汇总多个执行状态时出现“多种执行状态”。已确认：待验收继续显示于首页、驳回全员恢复未完成、历史任务也统一。

## Goals / Non-Goals

**Goals:** 同一任务所有当前接收人共享完成状态、申请和验收结果，事务和通知一致，保留个人记录和版本校验。

**Non-Goals:** 不合并重复任务的不同日期，不更改任务发布审批、个人历史和既有个人任务最高权限无上级的自完成例外，不新增服务或接口。

## Decisions

- task 新增 completion_status（NOT_COMPLETED/AWAITING_ACCEPTANCE/COMPLETED）作为完成状态来源；同步当前 task_assignment 的兼容执行状态，使旧客户端也获得一致结果。
- 完成写入先锁 task 再锁执行关系；申请人仍只能操作本人有效执行关系，校验其版本。全员进入待验收时版本递增，其他接收人的旧版本请求失败；每任务只新增一条申请，保留提交人和备注。
- 验收人沿用发起人验收；任务发起人也是接收人时统一由该任务最近审批人验收，防止通过另一接收人提交绕过自验收限制。现有个人创始人无审批人时的自完成保持不变。
- 验收通过或驳回同步所有有效接收人；通知通过既有事务内通知/推送队列发送，使用同一事件去重键按用户去重。个人执行记录不删除，相关批量变更纳入审计。
- 有待验收或已完成结果时拒绝改变接收人集合，避免移除申请人破坏验收或新增接收人重新制造混合状态；普通内容编辑保持既有权限。
- V17 数据迁移按任务统一：当前接收人已有完成则全部完成，并复用既有真实完成人/时间；否则已有待验收则全员待验收。旧多条待验收申请保留历史，在队列/详情中只提供一个当前操作入口，一次验收统一解决该任务的全部旧待验收申请。
- Android DTO 接收 completionStatus，公共文案为“未完成”“已完成”“已完成，待验收”。待验收使用警示色及说明，不当作正式验收完成；首页只隐藏正式完成。旧接口缺少新字段时提供兼容回退。
- 沿用消息轮询/前台推送触发当前任务页刷新；提醒偏好只控制弹窗，不阻止服务端状态同步。返回前台时也刷新，详情后台读取保留当前编辑记录。首页刷新丢弃旧分页请求结果，避免过期条目重新混入。
- 首页任务看板及其展开列表仅为待验收任务备注“待验收”，普通未完成任务不渲染状态文字或空行；任务详情与任务汇总页沿用完整状态文案。

## Risks / Trade-offs

- 批量状态变化扩大并发影响 → 固定 task→assignment 锁序、事务、版本及幂等回归验证。
- 历史迁移不可通过简单回滚代码恢复逐人状态 → 部署前备份数据库；迁移不删除任何历史记录，不在本任务部署生产。
- 客户端需要服务端支持才能同步其他人 → 必须先发布后端，再发布 Android；本任务交付代码及检查结果。

## Migration Plan

在独立测试数据库验证 V16→V17 迁移及多人状态场景，再进行后端和 Android 模块检查。生产部署与备份另行执行，不归档尚未合并的变更。
