## Context

基线为 `origin/dev` 的 `000bf2c`。Java 21/Spring Boot 已实现基于 Bearer 会话的认证、组织范围、员工状态、任务审批、日报、消息、操作记录。实际数据库为 H2，迁移截止 V17。Web 有 Vite 代理与管理布局，Android 有 Compose 五入口，原 Android 默认连接一期站点。现有部署监听 dev 推送。

## Goals / Non-Goals

提供六类 CRM 功能和一次隔离演示。商城订单同步、支付、财务、客户商业合同、自动绩效及生产发布延期。

## Decisions

- 使用 `dev2` profile、专用 H2 文件及附件目录。CRM 迁移使用额外的 Flyway location，先核验数据源再执行。默认 profile 沿用 V1–V17。Web 代理指向 19082，Android 使用带后缀的本机演示构建及独立会话。
- CRM 表统一带企业键，外键与员工表复合关联，使用现有员工账号 ID。业务独立维护，V0.1 每条业务关联一个客户，最多 50 名参与员工，参加业务本身不授予客户档案访问。编辑使用版本校验。
- 管理员和创始人读写本企业客户、业务与会员。部门经理及组长可查询本人和现有组织授权范围内负责的客户和业务。员工查询本人负责的客户，以及本人负责或参与的业务。Android 使用本人筛选。合同仅本人及本企业管理员可读取，管理员维护。以上授权矩阵为待甲方确认。
- 合同按企业业务日计算到期或临期状态，提前 30 天在合同列表提示。合同附件保存为受控 PDF 下载，使用 10 MiB 上限和随机存储名。所有写入记录资源 ID、动作和版本，不保存个人联系方式、附件内容或合同细节到通用操作日志。
- Web 使用现有 React 管理壳和会话。Android 在「我的」追加查询入口。沿用现有业务异常响应。

## Risks / Trade-offs

附件和数据库需要联合备份。临期提醒为页面提示，站内通知及推送待确认。客户分类为自由录入。业务阶段采用计划、进行、完成、取消。会员权益按单项维护，使用记录逐条保存服务状态。持久化员工引用需兼容现有软删除。

## Migration Plan

从干净二期库执行 V1–V17 和 CRM 迁移，再以纯虚构数据初始化企业。额外使用临时一期基线库验证保留原始数据。回退时恢复二期专用备份或继续运行基线独立实例。

## Open Questions

确认股东、合伙人、财务和行政所需的读写范围与字段；确认多客户业务、员工职责标准、客户合并、会员权益计数、续签、附件类型、提醒对象与通知渠道。
