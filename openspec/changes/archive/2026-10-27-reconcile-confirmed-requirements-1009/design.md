## Context

本轮已经逐项确认：每天一篇日报、日报多工作条目、个人重要事项选条目、个人任务自建上级审且本人完成、企业共用主次标签、AND 筛选、导图消息审核预留以及账号/显示设置。三端工程保留，正式接口和真实数据库尚未建立。

## Goals / Non-Goals

**Goals**：形成一套需求—架构—数据—接口—验收一致的新文档基线，旧编号沿用、新增编号顺延；原件保留、未定规则隔离，供用户后续提交 dev。

**Non-Goals**：修改任何运行代码、SQL 迁移、依赖、生产环境或 Git 历史；实现消息审核 UI；将未确认最高级审核、驳回重提和长期草稿保存定案。

## Decisions

1. 新版文件独立版本化，保留三份原件与旧架构/数据库，docs/README 只更新导航。第二章与完整版共用准确正文，完整版第3章整合概要并链接详细设计；不自动填造后续章节实现证据。
2. 日报头保存归属日期及发布事实，work_log_entry 保存完整工作条目，个人选择改引用 entryId。相较保留“多日志”或按全文字符串拆条，唯一日报与稳定条目 ID 能避免选错内容；发布日志最多一篇，草稿不混入已发布。
3. task_kind 区分 PERSONAL / DELEGATED；个人任务发起人=唯一接收人，经过直接上级批准后由本人完成，不创建待发起人验收申请。派发任务保留每接收人验收流程。两个完成来源分开留事实，避免自验收或伪造上级验收。
4. tag 是企业内共享目录；关联记录明确一项主标签与次标签，第一项主标签决定任务颜色，日志不染色；筛选命中全部 ID，不能只在主标签上筛。主次是对象内角色，不是标签树。
5. 逻辑模型预留标签挂整篇日报，条目引用日报标签；若需逐条打标签，应另确认并调整关系，不伪称已确认这种粒度。引用方式决定名称/颜色维护后动态展示，是技术建议而非新业务确认。
6. 消息审核预留 notice 记录与 reviewId 关联，并设计读取/已读/审核契约；服务端按任务审核权限再次验证，消息存在不等于有审核权。只设计，不落地入口和消息推送。
7. 密码/退出是服务端安全契约；字体/主题先用按账号隔离的客户端本地设置，不添加跨设备同步业务。对完整流程使用 Markdown 契约，不新增服务器 Controller 或真实表。

## Risks / Trade-offs

- 日报唯一性影响多处旧描述 → 全文检查 US/FR/场景/权限/统计/追踪表及两份正文一致性。
- 主标签与“第一个”顺序混淆 → 明确主次角色与输出主标签优先，单独存主标签引用并验证同企业、关联一致。
- 个人完成误用既有验收 → 字段记录 SELF 与 CREATOR_ACCEPTANCE 两种完成来源并做状态/权限分支。
- 未定审核阻塞最高级发起人 → 不默认自审/免审，接口返回策略未定；不生成假审核人。
- 文档似乎意味着代码完成 → 所有API/数据/流程标明目标契约，接口预留阶段不等于实现。

## Migration Plan

无运行数据迁移；新文件为 V1.3 需求、A0.2、DB0.2、API0.1。旧输入保持不变。未来从 LoFi 选取文档提交 dev 的操作由用户另行授权，不能混入现有 Android 工作区修改。若未来已有真实多日志数据，迁移方案须独立评审，本次不执行。

## Open Questions

最高级审核、原任务驳回重提、正式任务草稿/日志长期草稿、同刻/跨日/时区边界、重要程度语义、选中条目编辑/过期联动、子任务关联及整体完成/统计口径保留；日志标签粒度及标签停用的历史策略单列，不阻止已确认能力文档设计。
