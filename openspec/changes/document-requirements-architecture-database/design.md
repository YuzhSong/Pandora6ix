## Context

组长提供 2026-10-09 三份需求草案，要求放入 LoFi 的 docs 并开始技术架构与数据库设计。现有 Android 为离线低保真，Web 与 Java 21 / Spring Boot 后端为工程基线；README 中 MySQL 仍在评估。工作区已有其他 Android / OpenSpec 修改，本变更不触碰。

## Goals / Non-Goals

**Goals**：完整保留三份来源；比对第二章一致性；独立记录冲突；提供可追溯、可评审的架构和逻辑数据库草案；区分确定规则与技术建议及待确认规则。

**Non-Goals**：修订正式需求正文、实现业务 API、创建数据库表或迁移、引入运行依赖与基础设施、提交推送或归档其他变更。

## Decisions

1. 原件放在 docs/requirements，使用逐字节复制与 SHA-256 校验；审查意见单列文档。相比原地改正文，保留组长交付版本更利于后续 GPT 修订和追踪。
2. 架构采用与当前技术栈兼容的模块化单体建议，Android / Web 只通过服务端访问数据。微服务不适合当前团队与 MVP；不声称安全层、持久化已完成。
3. 数据库仅交付概念/逻辑设计，MySQL 8.4 / InnoDB 是待团队评审的技术建议，不执行 SQL。覆盖租户隔离、多人执行、审核、验收、日志和导图选择；草稿长期持久化、日志可选关联、最高负责人审核等另列决策门。
4. 技术时间戳与业务日期/时刻分开；全天与定时均来自同一任务记录，日历横条分段不形成数据库任务副本。
5. 以 FR 编号追踪设计；原文存在冲突时写出优先解释及保留问题，不能以原型行为替代业务定案。

## Risks / Trade-offs

- 需求仍为草案 → 未决条款不进入强制表约束或默认业务分支。
- 架构文档容易被误认为已实现 → 每份设计注明现状、目标与验证边界。
- 多人任务与多人审核容易混为一谈 → 审核针对一次派发，执行进度与完成验收针对每位接收人。
- 组织树与人的直属上级不总一致 → 分别建模，审核人取发起人的人员汇报关系，服务端验证范围。
- 保存原件的 Markdown 转义可能影响渲染 → 不改原件；独立导航与审查记录说明问题。

## Migration Plan

本次无运行系统迁移。后续仅在需求确认、独立 OpenSpec 批准和模块检查后添加依赖、迁移与业务代码。回退本变更可移除本次新增文档，不动既有工作。
